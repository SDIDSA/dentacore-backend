# Dentacore Backend

## Purpose
Node.js/Express REST API for the Algerian Dental Management System. Serves as the data and business logic layer for the JavaFX frontend.

## Ownership
- `server.js` — Entry point (starts Express + Socket.IO + appointment reminder scheduler)
- `prod.ps1` / `prod.sh` — Self-contained production bootstrap + startup (shipped in the hosting zip): downloads Node.js + PostgreSQL binaries into `.prod-tools/`, starts a local PG instance via `pg_ctl`, creates `.env` with generated secrets on first run, provisions the DB role + database, applies schema, installs deps, runs `node server.js`. PG data persists in `.prod-tools/pgsql/data/` across runs; Ctrl+C stops PG gracefully. Flags: `--systemd`/`-Service`, `--seed`/`-Seed`, `--backup-cron`/`-BackupCron`, `--port`/`-Port`, `-Domain` (downloads + caches the local Caddy `caddy.exe` into `.prod-tools/caddy/` — same self-contained pattern as Node/PG, no winget/system dependency — and installs it as a reverse proxy with auto-TLS on Windows). Windows uses EDB binaries; Linux uses Percona binaries. `prod.sh` must be LF-only
- `package-backend.ps1` — Windows packaging script producing `dist/sera-backend-<version>.zip` for hosting: regenerates the site brand assets (`brand-site.ps1`), stamps the website (`window.APP_NAME` in `site-head.js` + constant-name bootstrapper hrefs in `index.html` from pom.xml), whitelist stages, stages the authored deploy assets + `docs/HOSTING.md` (LF-normalized), per-file `node --check` gate, .NET ZipArchive with `/` separators. **All backend-website branding + stamping lives here** (`deploy.ps1` does not touch backend `public/` for stamping). `deploy/` holds supporting assets (sera.service, backup scripts, nginx sample, backup cron) referenced by the merged prod scripts
- `brand-site.ps1` — Repo-only **build tool** (not shipped in the zip): regenerates the site brand assets (`public/favicon.ico`, `public/icons/task-icon.svg`, and the inline `.brand-mark` SVGs in `public/index.html`) from `branding/identity.svg`, mirroring the client pipeline's `deploy.ps1` Phase 1.5 site outputs. Idempotent; ImageMagick optional (favicon skipped without it, SVG assets still regenerate). Invoked by `package-backend.ps1` before staging `public/`
- `deploy/` + `README-HOSTED.txt` — Authored deployment assets shipped in the hosting zip (kept LF-only). **Ubuntu**: `sera.service` (systemd unit template with `__APP_DIR__`/`__SVC_USER__` placeholders); `sera-backup.cron` (nightly `pg_dump -Fc`, 14-day dump retention, optional rclone offsite copy via `OFFSITE_REMOTE`, `audit_logs` trim at 180 days; runs as the app user `__SVC_USER__`, not `postgres`); `backup.sh` (standalone backup runner — connects to the self-contained PG in `.prod-tools` over TCP with `.env` credentials); `nginx-sera.conf` (reverse proxy sample). **Windows**: `backup.ps1` (uses `.prod-tools\pgsql\bin` tools preferentially, falls back to a system PG, connects as the dentacore app role). TLS on Linux terminates in nginx + certbot; on Windows, `-Domain` flag in `prod.ps1` downloads the self-contained Caddy binary and installs it with auto-TLS (`trust proxy = 1` expects exactly one hop). Full bootstrap (Node/PG install, DB provisioning, secrets, schema) is handled by `prod.sh`/`prod.ps1` on first run — no separate setup scripts
- `public/` — The **entire public website**, served same-origin by `express.static` (nginx `location /` proxies to Express; there is no separate static host — the old surge deployment was removed 2026-08-26): `index.html` + `style.css` + `icons/` (marketing site; the constant-name bootstrapper hrefs (`Sera-Bootstrapper.exe`) are stamped into `index.html` by `package-backend.ps1` at package time; the page's scripts are externalized to `site-head.js` + `site-body.js` for helmet's CSP `script-src 'self'`, with `window.APP_NAME` living in `site-head.js` and stamped there by `package-backend.ps1`), `book.html`/`book.js` (booking portal), `signup.html`/`signup.js` (clinic self-signup), `platform.html`/`platform.js` (**operator console** — the Sera owner's cross-tenant admin; login gates on `auth.role.platform_admin`, token in `sessionStorage`, `noindex`), shared `portal.css` (token set + common components, incl. `--grid-line`) and `site.js` (pre-paint lang/theme resolution + header switchers, persists `dc-lang`/`dc-theme`). Page scripts are externalized for CSP; `dev-tools/` (repo-only, not packaged) audits rendering via CDP. All website branding (favicon, `icons/task-icon.svg`, inline `.brand-mark` SVGs) and stamping (`window.APP_NAME` + bootstrapper hrefs) is done by the backend pipeline (`package-backend.ps1` → `brand-site.ps1` + its stamp step) — never by the client `deploy.ps1`
- **Public-page design language (durable)**: `book.html` and `platform.html` follow the marketing site's "instrument datasheet" art direction — grid-paper background from `--grid-line`, hairline rules with corner registration ticks, numbered mono section labels (`01`–`05`), square corners (0 radius), Fira Code mono for all numbers/labels/status pills, one brand blue, brand header = inline SVG mark + `sera` wordmark + hairline divider + page title. `signup.html` intentionally stays on the plainer `portal.css` look for now. When touching these pages, preserve every element id + `data-i` hook the page scripts bind (verified by hook-audit before commit) and re-run `dev-tools/slot-color-check.ps1` for book.html (buttons don't inherit body color — a past bug class)
- `scripts/create-platform-admin.js` — provisions/promotes the platform owner account (`auth.role.platform_admin`) under the reserved `sera-platform` tenant; usage in the script header
- `src/app.js` — Express app factory
- `src/socket.js` — Socket.IO real-time event bus
- `src/config/` — Database, Swagger, Cloudinary, error, and logger config
- `src/middleware/` — Auth, audit, rate limiting, error handling, response formatting, API usage logging
- `src/routes/` — 19 entity route modules + `publicBookings.js` (public booking portal) + `signup.js` (public clinic self-signup) + `platform.js` (operator console API)
- `src/services/` — Business logic (notifications, reminder scheduling)
- `src/utils/` — CSV, logger, pagination, upload, availability helpers
- `src/__tests__/` — Jest test suite (runs against a seeded local DB; `jest.setup.js` forces `NODE_ENV=test` to bypass rate limiting; 182+ pass across 16 files incl. `platform.test.js` with 46 tests)
- `scripts/` — DB recreate, seed, verify utilities
- `.github/workflows/ci.yml` — CI pipeline (bootstraps the DB from `db.sql` + `seed-prod.sql` + `seed.sql` via psql, then runs `npm test`; no Docker image build)
- `db.sql` — Full **schema** (DDL) source of truth (applied via `recreate-db.*`, CI, and hosting setup). **Idempotent**: every table/index uses `IF NOT EXISTS`, triggers use `CREATE OR REPLACE TRIGGER`, so hosting re-deploys re-apply it safely over an existing database. `db.sql` is pure DDL — it contains **no seed/data** statements.
- `seed-prod.sql` — Production **system seed** (role rows, `platform_plans`, global `treatment_categories`). Idempotent and applied as its OWN psql step after `db.sql` (so it runs even when `db.sql` aborts on a re-apply under `ON_ERROR_STOP=1`). Run on every provisioned database; required for the app to function (signup needs the roles, the booking portal needs the global categories).
- `seed.sql` — Optional **demo data** (3 clinics) for dev/CI only; NOT applied in production.

## Local Contracts
- Route responses are returned bare (arrays/objects directly via `res.json`); `src/middleware/responseFormatter.js` exists but is **not mounted** in `src/app.js` — do not claim a `{ data, meta }` envelope on the wire
- Auth via JWT bearer tokens, middleware in `auth.js`; access/refresh expiry defaults to `24h`/`7d` when `JWT_EXPIRES_IN`/`JWT_REFRESH_EXPIRES_IN` are unset
- Rate limiting applied to all mutation routes via `rateLimiter.js` — `apiLimiter` (60/min) and `mutationLimiter` (30/min) are mounted **before** the routers in `src/app.js`; `mutationLimiter` counts mutation methods only (GET/HEAD/OPTIONS skip); both are bypassed when `NODE_ENV=test`. `src/app.js` sets `trust proxy = 1` (the nginx hop) so per-IP limits see real client addresses behind the reverse proxy
- Audit logging via `auditLogger.js` middleware (in-memory queue capped at 1000 entries); DB-side retention is handled by the hosting box (`deploy/backup.sh` trims `audit_logs` older than 180 days)
- API usage logging via `apiUsageLogger.js` (non-blocking, writes to `api_usage_logs`, auto-prunes entries >30 days); mounted after `auditLogger` in `src/app.js`
- Stack traces hidden in production (`NODE_ENV=production`); production 500s also return the generic `error.internal_server` key and fire an optional `ERROR_WEBHOOK_URL` alert
- Logs mirror to `logs/backend.log` with size rotation (`LOG_FILE=false` disables); unhandled rejections are logged and uncaught exceptions trigger graceful shutdown
- Swagger docs production-guarded (disabled when `NODE_ENV=production`)
- Database access via Kysely query builder with PostgreSQL
- All DB scripts read `DB_PASSWORD` from `.env`; no hardcoded credentials
- **No Docker path**: `Dockerfile`/`docker-compose.yml`/`.dockerignore` are removed — production deploys are zip-upload to a Linux host (see `package-backend.ps1` + `docs/HOSTING.md`); local dev runs natively (`recreate-db.*`). The old local Windows topology (`setup-backend.ps1`, bundled installers, `restore-db.ps1`) was deleted 2026-08-25 with the hosted-SaaS commitment
- **Prod startup**: `prod.ps1` (Windows) / `prod.sh` (Linux) — single-script production bootstrap + startup shipped in the hosting zip. Self-contained: downloads/caches Node.js (22.16.0) + PostgreSQL binaries into `.prod-tools/` (Windows = EDB binaries, Linux = Percona binaries, and with `-Domain` on Windows also downloads Caddy into `.prod-tools/caddy/caddy.exe`), starts a local PG instance via `pg_ctl` on port **5434**, keeps data in `.prod-tools/pgsql/data/` across runs, and stops PG gracefully on exit (`finally`/`trap`). First run (no `.env`): generates secrets, then `initdb -U $DB_USER` creates the role; the role's password is set to match `.env` over **temporary local trust auth** on first init, then `pg_hba.conf` is locked down to md5; schema applied idempotently. Subsequent runs: skips provisioning, verifies PG connectivity, applies schema, installs `--omit=dev`, runs `node server.js`. The server runs in the foreground (Ctrl+C stops it). `pg_ctl -l` uses a distinct `pg_ctl.log` so it never collides with `logging_collector`'s `pg.log` (a Windows sharing-violation bug). Flags: `--systemd`/`-Service`, `--seed`/`-Seed`, `--backup-cron`/`-BackupCron`, `--port`/`-Port`, `-Domain` (downloads the self-contained Caddy into `.prod-tools/caddy/caddy.exe` and installs it with auto-TLS on Windows; no winget/system dependency). No data cleanup on exit. `prod.sh` must remain LF-only. **Direct HTTP-only test (no TLS/proxy)**: `prod.ps1` and `prod.sh` both default to **port 80** so plain `.\prod.ps1` / `bash prod.sh` serve both the site + API at `http://<host>/`. Ports <1024 need elevated rights: `prod.ps1` enforces a guard (run in an Administrator console or `-Service` as SYSTEM); `prod.sh` runs as root (or `CAP_NET_BIND_SERVICE`). Re-home to 4000 when a reverse proxy fronts 80/443: `prod.ps1` under `-Domain` (Caddy), `prod.sh` under `--systemd` (the service runs unprivileged + follows the nginx/certbot TLS path). Skip the proxy entirely for the HTTP-only path
- **Public booking surface (prototype)**: `/api/v1/public/:clinic/*` (see `routes/AGENTS.md`) + `public/book.html` portal page (client script externalized to `public/book.js` — helmet's default CSP `script-src 'self'` blocks inline scripts) served by `express.static('public')`; phone fields in `signup.html`/`book.html` accept local Algerian formats (`0549468120`, `05 49 46 81 20`, `00213…`, `+213…`) and normalize to E.164 via the vendored `public/libphonenumber.min.js` + `public/phone.js` (`normalizeDZPhone`, region `DZ`) — mirroring the desktop client's `libphonenumber` normalizer; the backend still requires E.164 (`+213…`), so never send raw local format to the API; clinic = tenant `subdomain` slug; availability driven by the `working_hours` table (in `db.sql`); `GET /:clinic/services` returns global + clinic-owned `treatment_categories` (global categories are idempotently seeded by `seed-prod.sql`, applied on every provisioned DB — incl. self-signup clinics — so the service list is never empty without running `seed.sql`); demo data via `node scripts/seed-demo-clinic.js` then open `/book?clinic=clinic-demo`. These public pages are served at clean extensionless URLs (`/book`, `/signup`, `/platform`) with `/foo.html` 301-redirected to `/foo` (see the `PUBLIC_PAGES` map in `src/app.js`); never link to or redirect users to the `.html` form. Schema changes go straight into `db.sql` — there is **no migration system** (runner, ledger, and `AUTO_MIGRATE` were removed 2026-08-25; existing deployed DBs are updated by applying psql changes manually)
- **Multi-role model (durable)**: roles are **equal** — there is NO primary/secondary distinction. `user_roles` (`user_id`, `role_id`) is the SOLE source of a user's roles; the legacy `users.role_id` column was removed. `get_user_by_email` (in `db.sql`) returns only `role_keys` (aggregated `TEXT[]` from `user_roles`). Auth tokens and `/login`+`/validate` responses carry `role_keys` (array); `role_key`/`role_id` in responses are a **derived display convenience** (admin-preferred) computed by `src/utils/roleUtil.js` `primaryRoleKey`, never authoritative. `POST /api/v1/users` and `PATCH /api/v1/users/:id` accept `role_ids` (array of role ids); all entries are written to `user_roles` (a PATCH with `role_ids` replaces the assignment). The `authorize(...roles)` middleware grants if `req.user.role_keys.includes(any)`. A tenant must always retain ≥1 `auth.role.admin`: role-changing PATCH, status deactivation, and DELETE all reject with `user.error.last_admin` when that would leave zero admins. The public booking `:clinic/dentists` query and booking dentist validation match purely on `user_roles` (`EXISTS user_roles WHERE role_id = dentist`), so a dentist who also holds admin still appears as bookable. The desktop client mirrors this via `HasRole.getRoles()`/`setRoles()` and `primaryOf` (display-only), and sends `CreateStaffRequest.role_ids`.
- **Default ports (durable)**: API HTTP `4000` everywhere (dev and CI; and behind nginx/Caddy which terminates TLS in front of it — re-homed to `4000` under the proxy: `prod.ps1 -Domain`, `prod.sh --systemd`). Exception: `prod.ps1`/`prod.sh` default port is **80** for direct HTTP-only hosting (serves site + API with no port; re-homed to 4000 under their proxy triggers). PostgreSQL: `5434` everywhere the self-contained prod scripts run (`prod.sh`/`prod.ps1` start their own PG on 5434 — no apt cluster, no `pg_lsclusters`); dev/CI also use `5434`. Frontend base URL defaults to `http://localhost:4000/` (`Service.java`, overridable via `-Ddentacore.api.url`). Dev CORS fallback includes `http://localhost:4000`. Production DNS lives in `docs/HOSTING.md`. Production ports/DNS live in `docs/HOSTING.md`
- Client updates ship via GitHub Releases on `SDIDSA/packages` consumed directly by the bootstrapper — there is no server-side `/api/v1/updates/*` channel anymore (removed 2026-08-25)
- Internet deployment runbook: `docs/HOSTING.md` (backups/maintenance cron included in `prod.sh --backup-cron`)

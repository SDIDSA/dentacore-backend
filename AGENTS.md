# Dentacore Backend

## Purpose
Node.js/Express REST API for the Algerian Dental Management System. Serves as the data and business logic layer for the JavaFX frontend.

## Ownership
- `server.js` — Entry point (starts Express + Socket.IO + appointment reminder scheduler)
- `package-backend.ps1` — Windows packaging script producing `dist/sera-backend-<version>.zip` for hosting: whitelist stage, stages the authored deploy assets + `docs/HOSTING.md` (LF-normalized), per-file `node --check` gate, .NET ZipArchive with `/` separators (Windows Compress-Archive writes `\`, which breaks Linux unzip). Nothing is bundled — `deploy/setup.sh` installs Node.js and PostgreSQL via apt on the target host
- `deploy/` + `README-HOSTED.txt` — Authored Linux deployment assets shipped in the hosting zip: `setup.sh` (full bootstrap: Node/PostgreSQL install, DB + role creation via **peer-auth socket access as the postgres user** (`runuser`/`su`, never passwordless TCP), aligns `DB_PORT` to the detected local cluster port (5432 — the template's 5434 is Windows/dev-only), schema apply, secrets generation, loud Cloudinary/CORS/seed-password go-live warnings, optional systemd unit, optional `--backup-cron [rclone-remote]` maintenance cron); an explicit `--port N` is rewritten into `.env` even when `.env` already exists (re-deploys honor it), `backup.sh` + `sera-backup.cron` (nightly `pg_dump -Fc`, 14-day dump retention, optional rclone offsite copy via `OFFSITE_REMOTE`, `audit_logs` trim at 180 days), `sera.service` (systemd unit template with `__APP_DIR__`/`__SVC_USER__` placeholders), `nginx-sera.conf` (reverse proxy sample). Edited directly — not generated by the packaging script. Keep them LF-only
- `public/book.html` + `public/book.js` — Public booking portal page (served by express.static; script externalized for CSP)
- `public/signup.html` + `public/signup.js` — Public clinic self-signup page (same CSP/theme/lang patterns as the booking portal; posts to `/api/v1/signup`)
- `src/app.js` — Express app factory
- `src/socket.js` — Socket.IO real-time event bus
- `src/config/` — Database, Swagger, Cloudinary, error, and logger config
- `src/middleware/` — Auth, audit, rate limiting, error handling, response formatting
- `src/routes/` — 19 entity route modules + `publicBookings.js` (public booking portal) + `signup.js` (public clinic self-signup)
- `src/services/` — Business logic (notifications, reminder scheduling)
- `src/utils/` — CSV, logger, pagination, upload, availability helpers
- `src/__tests__/` — Jest test suite (runs against a seeded local DB; `jest.setup.js` forces `NODE_ENV=test` to bypass rate limiting)
- `scripts/` — DB recreate, seed, verify utilities
- `.github/workflows/ci.yml` — CI pipeline (bootstraps the DB from `db.sql` + `seed.sql` via psql, then runs `npm test`; no Docker image build)
- `db.sql` — Full schema source of truth (applied via `recreate-db.*`, CI, and hosting setup). **Idempotent**: every table/index uses `IF NOT EXISTS`, triggers use `CREATE OR REPLACE TRIGGER`, so hosting re-deploys re-apply it safely over an existing database

## Local Contracts
- Route responses are returned bare (arrays/objects directly via `res.json`); `src/middleware/responseFormatter.js` exists but is **not mounted** in `src/app.js` — do not claim a `{ data, meta }` envelope on the wire
- Auth via JWT bearer tokens, middleware in `auth.js`; access/refresh expiry defaults to `24h`/`7d` when `JWT_EXPIRES_IN`/`JWT_REFRESH_EXPIRES_IN` are unset
- Rate limiting applied to all mutation routes via `rateLimiter.js` — `apiLimiter` (60/min) and `mutationLimiter` (30/min) are mounted **before** the routers in `src/app.js`; `mutationLimiter` counts mutation methods only (GET/HEAD/OPTIONS skip); both are bypassed when `NODE_ENV=test`. `src/app.js` sets `trust proxy = 1` (the nginx hop) so per-IP limits see real client addresses behind the reverse proxy
- Audit logging via `auditLogger.js` middleware (in-memory queue capped at 1000 entries); DB-side retention is handled by the hosting box (`deploy/backup.sh` trims `audit_logs` older than 180 days)
- Stack traces hidden in production (`NODE_ENV=production`); production 500s also return the generic `error.internal_server` key and fire an optional `ERROR_WEBHOOK_URL` alert
- Logs mirror to `logs/backend.log` with size rotation (`LOG_FILE=false` disables); unhandled rejections are logged and uncaught exceptions trigger graceful shutdown
- Swagger docs production-guarded (disabled when `NODE_ENV=production`)
- Database access via Kysely query builder with PostgreSQL
- All DB scripts read `DB_PASSWORD` from `.env`; no hardcoded credentials
- **No Docker path**: `Dockerfile`/`docker-compose.yml`/`.dockerignore` are removed — production deploys are zip-upload to a Linux host (see `package-backend.ps1` + `docs/HOSTING.md`); local dev runs natively (`recreate-db.*`). The old local Windows topology (`setup-backend.ps1`, bundled installers, `restore-db.ps1`) was deleted 2026-08-25 with the hosted-SaaS commitment
- **Public booking surface (prototype)**: `/api/v1/public/:clinic/*` (see `routes/AGENTS.md`) + `public/book.html` portal page (client script externalized to `public/book.js` — helmet's default CSP `script-src 'self'` blocks inline scripts) served by `express.static('public')`; clinic = tenant `subdomain` slug; availability driven by the `working_hours` table (in `db.sql`); demo data via `node scripts/seed-demo-clinic.js` then open `/book.html?clinic=clinic-demo`. Schema changes go straight into `db.sql` — there is **no migration system** (runner, ledger, and `AUTO_MIGRATE` were removed 2026-08-25; existing deployed DBs are updated by applying psql changes manually)
- **Default ports (durable)**: API HTTP `4000` everywhere (dev and hosted; nginx terminates TLS in front of it). PostgreSQL: `5434` is the **Windows/dev** port only (`recreate-db.*`, `test-db-connection.js`); hosted Linux uses the apt cluster's `5432` — `deploy/setup.sh` detects it via `pg_lsclusters` and rewrites `.env`. Frontend base URL defaults to `http://localhost:4000/` (`Service.java`, overridable via `-Ddentacore.api.url`). Dev CORS fallback includes `http://localhost:4000`. Production DNS lives in `docs/HOSTING.md`. Production ports/DNS live in `docs/HOSTING.md`
- Client updates ship via GitHub Releases on `SDIDSA/packages` consumed directly by the bootstrapper — there is no server-side `/api/v1/updates/*` channel anymore (removed 2026-08-25)
- Internet deployment runbook: `docs/HOSTING.md` (backups/maintenance cron included in `deploy/setup.sh --backup-cron`)
